# YANG Version Support — Transition Plan

This doc tracks the move from the `pr/johalley/nac-writer-update` branch's
runtime override-table mechanism to a per-release ygot-typed architecture.
It complements `docs/yang-version-support.md`, which describes the current
mechanism in operational detail.

The full reasoning behind each phase lives in the adversarial-review +
action-plan conversation. This file captures only the *delta*: what is
done, what is gated, and what each gate needs.

## What Phase 1–3 delivered

- **Bridge safety floor.** `SetDeviceVersion` now rejects malformed strings
  and rejects versions not in `deviceVersionToReleaseTag` with a typed
  `ErrUnsupportedDeviceVersion`. Both the aggregator and the cisco-vk
  reconciler propagate the error class to Kubernetes Events
  (`UnsupportedDeviceVersion` vs `MalformedDeviceVersion`).
- **Symmetric Fetch path.** `singletonWriter.Fetch` and
  `keyedListWriter.Fetch` now call `AutoReverseObservedBody`, which
  reverses `ElementMap` + `EmptyLeaves` for families whose override has
  no `BodyTransform`. Families with `BodyTransform` (snmp_server,
  logging) keep their hand-written reverse logic; the helper is a no-op
  for them by design.
- **Deferred-dial → version refetch.** When the startup dial loses the
  apphosting+VK race and the deferred-dial retry loop succeeds 30s
  later, the loop now refetches the device version and reapplies it via
  `dctx.ApplyDeviceVersion()`. Pre-fix, writers stayed on baseline shape
  forever in that case.
- **Status-aware release loader.** `LoadYANGReleaseTags` now distinguishes
  `supported`/`experimental`/`deprecated` releases and rejects unknown
  statuses. Releases 1715, 1716, and 1718 are declared in
  `schema/yang-versions.yaml` (1715/1716 marked experimental until
  Phase 3.3 vendors their YANG modules).
- **Per-release ygot output.** `cisco-vk-yang-sync` now emits
  `outTypes/<release-tag>/iosxe_config.go` with package `xe<tag>` when
  `--yang-version` is set. The legacy single-package layout still works
  when the flag is empty.
- **Fixture harness.** `writers/fixtures/<release>/<family>/<case>/`
  is walked by `TestFixturesAgainstRegisteredWriters`. Two
  fixtures (`1716/snmp_server/basic` and `1716/snmp_server/noop`)
  prove the mechanism; adding a fixture is a no-code change.
- **Migration readiness.** `tools/cvk-netascode-migrate` inspects
  netascode-shaped YAML, reports which top-level families CVK manages
  from `schema/families.yaml`, and leaves unsupported top-level
  families as silent passthrough. Its `emit-cr` subcommand emits a
  starter `IOSXEConfig` with `managedFamilies` inferred from supported
  families in the input.
- **Parity matrix.** `make parity-matrix` regenerates
  `docs/family-parity.md` from `schema/families.yaml`;
  `make check-parity-matrix` fails when the checked-in matrix is stale.
- **Passthrough invariant.** `TestLeafPassthroughPreserved` pins that
  untyped writers preserve unmodelled leaves explicitly present in
  desired intent. Phase 5 and later typed-writer work must keep this
  invariant green before any family moves to typed output.

## Migration readiness

The migration surface is intentionally additive. Operators can run:

```text
cvk-netascode-migrate path/to/device.nac.yaml
cvk-netascode-migrate emit-cr --name edge-01 path/to/device.nac.yaml
cvk-netascode-migrate matrix --output docs/family-parity.md
```

The report separates supported families from unsupported passthrough
families. `emit-cr` uses only the supported set for
`spec.managedFamilies` while keeping the source body intact under
`spec.source.inline`, so non-CVK data is not silently converted into a
managed family.

When `spec.managedFamilies` is empty, the resolver now infers it from
the top-level keys of the resolved configuration. An explicit list still
wins and remains the recommended production posture for tight ownership.

## CI Tiers

| Tier | Scope | Merge gate |
|------|-------|------------|
| T0 | Unit tests, fixture tests, generated-doc drift, parity matrix drift, `go build ./...`, `go vet ./...`, `go test -race -count=1 ./...` | Blocks every merge. |
| T1 | Live lab against a real IOS-XE device for transport/version paths | Blocks release branches and any change that touches transport, engine transactionality, or version resolution. |
| T2 | Chaos and failure injection: reconnects, candidate lock contention, rollback, confirmed-commit fallback | Blocks changes that claim resilience or alter rollback/transaction semantics. |
| T3 | Scale and soak: many CRs/devices, metric cardinality, informer/cache pressure | Advisory for normal merges; blocks production enablement of new broad reconciliation modes. |

The skeleton `.github/workflows/tiers.yml` documents this gate model
without enabling production schedules. T0 is the only default CI tier;
T1-T3 stay manual until lab capacity and ownership are explicit.

## Gates blocking Phase 3.3 onwards

### Phase 3.3 — vendor YANG modules

**Status:** 1718 is vendored for this phase. 1715 and 1716 remain
unvendored by design.

**Resolution:** `make vendor-yang RELEASE=1718` vendors the pinned
YangModels tree into
`internal/drivers/iosxe/configdriver/schema/yang/1718/` and writes
`.provenance.yaml` beside it. Upstream currently names the 17.18.1
bundle `17181`; the local release tag remains `1718`.

### Phase 3.4 — generate ygot packages

**Blocker:** 1718 ygot generation reaches the generator and currently
fails with `augment: already set`. The native YANG tree is large; expect
single-package output in the 100K-line range per release once the ygot
augment/import issue is resolved.

**Resolution:** after vendoring, run
`go run ./tools/cisco-vk-yang-sync --yang-version=1718 --yang-dir=schema/yang/1718 --dry-run=false`
once per supported release. Vendor the generated packages and add a CI
step that regenerates and diffs against the checked-in copies.

### Phase 4 — release-aware Lookup

**Blocker:** `iosxebuilder.LookupWriter(family) writers.SectionWriter`
takes no release argument today; same for `UnionWriterPaths`. Changing
the signature is a cross-cutting refactor (engine, aggregator, cisco-vk,
deviceoperation reconciler) that needs the typed-writer adapter from
Phase 5 alongside it to avoid landing a half-built dispatch spine.

**Resolution:** land Phase 4 and Phase 5 as a single change once the
generated packages exist; introduce a `TypedSectionWriter` adapter and
flip `LookupWriter(release, family)` in the same PR.

### Phase 5–7 — typed pilot, migration, retirement

These remain straightforward once Phases 3.3–4 are in place. The action
plan in the review conversation gives the per-family migration order
(simple ElementMap-only first, BodyTransform last, bgp + prefix_list
absolute last).

## What does NOT change as part of this transition

- The `IOSXEConfig` CRD shape. `spec.targetYangVersion` is already the
  CR-level surface for picking a release; nothing here changes that.
- Phases 3.3 and 3.4 have zero migration-shape impact: they vendor
  source YANG and generated Go types only. Operator netascode YAML,
  `IOSXEConfig.spec.source`, and `managedFamilies` semantics stay stable.
- Phase 5 and later must keep the passthrough invariant green before
  any typed writer replaces an untyped writer.
- The aggregator vs per-pod dispatch model — that's a separate axis.
- The CiscoDevice controller's deployment-selection logic — release-
  awareness is a runtime decision, not a deployment decision.

## Adding a new IOS-XE release after the migration completes

After Phase 7, supporting a new IOS-XE release is:

1. Add `(major, minor) → tag` entry to `device_release_map.go`.
2. Add `version: <tag>` block to `schema/yang-versions.yaml`.
3. Vendor YANG modules under `schema/yang/<tag>/`.
4. Run `cisco-vk-yang-sync --yang-version=<tag> --yang-dir=schema/yang/<tag>`.
5. Add a fixture set under `writers/fixtures/<tag>/<family>/` for any
   family whose wire shape diverges from the baseline.
6. CI green.

No writer code changes.
