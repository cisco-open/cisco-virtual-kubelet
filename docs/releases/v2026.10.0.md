# v2026.10.0 release candidate

Target release date: **2026-10-01**  
Status: **unpublished release candidate**

This page describes the planned October release. It is not a release artifact
reference until the tag, images, chart, checksums, and signatures appear on the
public [Releases page](https://github.com/cisco-open/cisco-virtual-kubelet/releases).

## Release scope

The release candidate combines the Kubernetes-native topology foundation with
the first IOS-XE rollout capabilities:

- manager-owned CiscoDevice-to-Node identity and bounded topology projection;
- native scheduler affinity and topology-spread placement;
- immutable IOS-XE rollout plans with topology-domain budgets, canaries, and
  pause/cancel recovery;
- topology-scoped image endpoint selection with frozen endpoint, digest, and
  Secret identity per target;
- secure gNOI transfer, activation, and verification through the existing
  IOS-XE software lifecycle; and
- an opt-in, PDB-aware Eviction drain for the explicitly supported workload
  subset.

The rollout and drain APIs remain alpha/preview contracts. Managed topology,
write-class gNOI, and workload drain are disabled by default and require the
administrator to opt in after completing the admission and rollback checks in
the [managed topology guide](../topology-awareness.md).

## Compatibility boundary

- Kubernetes 1.35 is the CVK support floor for managed topology.
- Kubernetes 1.37 native TAS is qualified as an independent experimental
  scheduler path; TAS is not a CVK runtime dependency and is not enabled by
  default.
- The public rollout implementation in this release is IOS-XE-specific.
  NX-OS and IOS-XR do not receive a generic rollout API from this release.
- The physical qualification evidence covers the IOS-XE lab fleet used by the
  project. It does not establish multi-site fault tolerance, zero-downtime
  guarantees, or cross-platform production support.

## Required release gates

The release candidate must be cut from the final merged commit, not from an
intermediate stacked branch. Before tagging, maintainers must record passing
results for:

1. `go test ./...` and `go test -race ./...`;
2. `go vet ./...`, build, and `go mod verify`;
3. generated deepcopy/CRD/RBAC parity and Helm lint/render checks;
4. the Kubernetes 1.35 real-API admission and default-scheduler suite;
5. secure gNOI upgrade and downgrade validation on the supported IOS-XE lab
   devices, including final Node, Pod, PDB, Lease, reservation, and device
   inventory evidence;
6. strict documentation build; and
7. vulnerability and dependency checks on the exact release commit.

Do not publish while a release check is failing or while a dependency update
has an unresolved vulnerability result. A failed dependency PR must be fixed
or explicitly deferred in the release decision; it must not be merged merely
to unblock the feature stack.

## Operational expectations

The supported upgrade path is a controlled relocation protocol. It protects
eligible Pods with Kubernetes Eviction and PDB semantics, waits for the exact
post-termination device inventory evidence, and releases the protection only
after the manager's fencing Lease and worker observations are settled. It is
not a promise of uninterrupted network forwarding or zero downtime.

Operators should retain the following evidence for every production change:

- the applied rollout and approval manifests;
- campaign and per-device phase transitions;
- CVK manager and worker logs with secret material redacted;
- IOS-XE console and `show` command evidence;
- final topology, Node, Pod, PDB, Lease, and reservation state; and
- the exact image digest and source endpoint selected for each target.

## Deferred roadmap

The following work is intentionally outside this release:

- durable image prefetch, shared cache, and cache-loss recovery;
- independently durable install/stage/activate reservations and resumable
  activation;
- general-purpose workload evacuation for StatefulSets, DaemonSets, Jobs,
  PVC-backed workloads, or custom controllers;
- an authoritative discovered topology graph or graph-cost scheduler;
- mandatory native Workload/PodGroup/TAS integration;
- generic NX-OS or IOS-XR rollout APIs;
- multi-cluster ownership and cross-controller fencing; and
- automated routing, forwarding, utilization, and critical-service health
  gates.

These items remain tracked in the [topology roadmap](../topology-awareness.md)
and should be delivered as separately qualified changes after the October
release.
