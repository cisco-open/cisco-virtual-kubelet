# Dynamic tag membership and causal Create verification

The existing shared tag executor was qualified against the lab for OR/EQ, AND-wrapped LIKE and ILIKE, and multi-value IN rules. Each isolated generated tag passed create, same-UUID update, first-device to second-device membership, matching-rule clearing, restoration, no-match and final empty-rule transitions. Each step used a fresh compiler, native rule readback, no-op verification and DYNAMIC/STATIC/MIXED provenance checks. All four exact-UUID fixtures were removed and their prior tag catalogs restored. These are controller metadata operations, with no device provisioning or upgrades.

The exact pinned NetAsCode consumer forwards `dynamic_rules` into the provider. The official [provider schema](https://github.com/CiscoDevNet/terraform-provider-catalystcenter/blob/main/docs/resources/tag.md) documents these operators; native evaluation, rather than request acceptance alone, is the evidence here.

A read-only inspection of the first original Create task found `serviceType=Grouping Service` and a canonical UUID in `data`, equal to the UUID later removed during cleanup. This supports a new candidate verification path using the existing task decoder and transport. It requires the original task identity/timestamps/completion/service/result UUID and matches that result against native tag readback. Name-only matching cannot complete Create verification. It does not publish creator ownership, adopt existing tags, or authorize pruning/deletion.

The task-bound verification and acknowledged-task recovery are now applied. The broader original binding regression passed 1,336 events; recovery passed 150 controlled/real-Kubernetes-API events, followed by 650 actual-worktree configuration/tag/example events. Recovery selects actual compiled tag leaves with their full group paths, requires the existing metadata-only task envelope, and composes prior callbacks without changing source/owner/controller checks or adding a state machine, transport, CRD or submission permit.

A second native qualification exercised the public combined inventory/templates manifest against isolated real Kubernetes persistence. Both Create and same-UUID Update were changed from Accepted to Unknown after retaining their original task receipts. Fresh reconciler instances recovered both original tasks and reached the current-generation InSync state. A strict transport allowlist counted exactly one POST and one PUT and refused unrelated/repeated mutations. Cleanup was supervised, required the original Create task result UUID, unchanged generated tag state and empty memberships, and restored the complete prior tag catalog. This does not claim manifest-driven deletion or installed actors.

The applied source and complete source-specific gates are in the machine-readable record. Creator/applied ownership receipts, pruning/deletion, interface rules and installed-cluster qualification remain open. Retain convergence and task recovery do not establish full tag resource parity.
