    SD-WAN controller deployment

    Alpha · introduced in v2026.11.1. Use matching CRDs, chart and image; October v2026.10.0 does not contain this adapter. Check the release records for publication and artifact availability.

    The independent sdwan adapter uses the existing CVK NetworkController worker and NetworkControllerConfig intent APIs. It calls SD-WAN Manager directly; the NetAsCode module and provider are source references for porting the data model, schemas, defaults and API behavior. Terraform is not a build, test or deployment dependency of the SD-WAN integration.

    Model contract

    The public model remains the upstream sdwan document. The format is netascode-sdwan, model version 1.5.0. The compiler currently supports:

    • edge_feature_templates.banner_templates: name, description, device types, login/MOTD literals and variables, including upstream device-type defaults.
    • edge_feature_templates.cli_templates, global_settings_templates, multicast_templates, cellular_controller_templates and cellular_profile_templates, bfd_templates, igmp_templates, ntp_templates, omp_templates, pim_templates, thousandeyes_templates, secure_app_hosting_templates, dhcp_server_templates, ipsec_interface_templates, snmp_templates, logging_templates and gre_interface_templates, including per-family device defaults and overrides. Generate their metadata with scripts/sdwan/generate-classic-definitions.py MODULE_CHECKOUT PROVIDER_CHECKOUT.
    • feature_profiles.system_profiles: profile name/description, banner, basic, BFD, global, OMP, NTP, logging, MRF, flexible port speed, performance monitoring, security, SNMP and AAA. feature_profiles.cli_profiles.config supports native CLI parcels. Scalar and nested-list definitions for basic/global/OMP/NTP/logging/security are generated from pinned module mappings and provider defaults/value schemas. Regenerate with scripts/sdwan/generate-parcel-definitions.py MODULE_CHECKOUT PROVIDER_CHECKOUT. Generated metadata retains the upstream MPL-2.0 license in definitions/LICENSE.
    • feature_profiles.transport_profiles.gps_features and other_profiles.ucse / other_profiles.thousandeyes, including the NaC GPS enable default and the ThousandEyes virtual-application wrapper. These fixtures are unattached.
    • feature_profiles.service_profiles.dhcp_servers, ipv4_trackers and object_trackers, ipv4_tracker_groups and object_tracker_groups, with native name-based parcel management and full generated API-data schema checks for these resources.
    • feature_profiles.transport_profiles.cellular_controllers and cellular_profiles, including authentication switches, credential variables and network slicing on the qualified 20.18 Manager. Inactive authentication fields and invalid slicing combinations are rejected before mutation.
    • configuration_groups: name/description and references to declared system, transport, service, CLI or other profiles. Device associations are not enabled.
    • Name/description mappings for the other eight profile collections, plus the automatically created application-priority settings parcel and visibility flags.
    • All 24 classic policy_objects collections, including named SLA probe references. Policy names are limited to 32 characters because this Manager rewrites longer names.
    • application_catalog.custom_applications: custom names, server names, L3/L4 rows and business relevance; the lab cannot qualify create until SD-AVC is enabled.
    • network_hierarchy groups/regions through levels 0–2 and unassigned sites with the 20.18 location/GPS model. Global collectors remain unsupported.

    deployment.yaml combines the baseline fixtures under one config and five managed sections. Use deployment-config.yaml with its resolved output instead of installing individual configs that would compete for the same section Lease. The combined fixture includes hierarchy prerequisites for region lists. For policy-objects-config.yaml, resolve policy-deployment.yaml so that the region prerequisite is included. system-features-config.yaml uses system-features.yaml as an alternative feature-profile section owner. The compiler allows up to 512 resources, bounded to 128 per section by journal capacity.

    Unknown fields and unsupported sections fail before mutation. Credentials and intent Secret injection are separate concerns: endpoint credentials work through projected files; intent secretRefs are currently rejected rather than ignored. No controller-specific API payloads appear in the public CRD.

    Resolve the qualified defaults outside the worker before declaring the source resolved. This retains upstream field names:

    go run ./cmd/cvk-sdwan-resolve examples/configs/sdwan/banner.yaml > /tmp/sdwan-banner.json
go run ./cmd/cvk-sdwan-resolve examples/configs/sdwan/system-profile.yaml > /tmp/sdwan-system-profile.json

    Deploy the qualified fixtures

    Install a matching CVK image and Helm chart. The chart adds the dedicated cisco-virtual-kubelet-sdwan-worker ClusterRole. Its namespace-scoped binding grants status updates and section Lease get/create/update; it grants no Secret API access, device mutation permission, or remote-deletion permission.

    Create the sdwan-lab namespace and a same-namespace sdwan-credentials Secret with username and password keys using your existing secret-management process. Do not put credentials into the model or commit them to the repository.

    kubectl create namespace sdwan-lab
kubectl apply -f examples/configs/sdwan/controller.yaml
kubectl -n sdwan-lab create configmap sdwan-banner-fixture \
  --from-file=model.yaml=/tmp/sdwan-banner.json
kubectl -n sdwan-lab create configmap sdwan-system-profile-fixture \
  --from-file=model.yaml=/tmp/sdwan-system-profile.json
kubectl apply -f examples/configs/sdwan/banner-config.yaml
kubectl apply -f examples/configs/sdwan/system-profile-config.yaml
kubectl -n sdwan-lab get networkcontrollers,networkcontrollerconfigs

    The examples initially report drift. Select spec.mode: apply to deploy the fixtures. Expect incremental Applying status followed by InSync after read-back verification. Reconciliation preserves existing matching resources without resubmitting their creation. An external object with the same name is a collision, not implicit authorization to adopt it.

    The lab manifest explicitly opts into insecure TLS because this endpoint's self-signed certificate has no IP SAN. Other deployments should supply a valid certificate and trust bundle. Sessions remain in process memory, rotate with projected material, and have bounded lifetimes. Redirects are rejected; only GET may refresh and retry after 401. Error bodies, cookies and tokens are not logged.

    Ownership and recovery

    Ownership is per controller UID, global scope and managed section. One config incarnation owns each section; separate configs cannot split the same section. Each worker session holds a 90-second Lease. Before a remote mutation, the worker persists a Dispatched receipt and rechecks the live endpoint/config/source and Lease bindings. A successful response persists the remote ID before verification.

    A settled Lease can transfer to a replacement worker for the same config after expiry. An unresolved dispatch blocks takeover and automatic replay. Such a failure requires investigation; an automatic uncertain-outcome recovery workflow is not implemented. Status reports OutcomeUnknown or SectionOwned without raw controller payloads. Never clear the journal merely to retry a timed-out POST.

    Retain is the supported prune/deletion policy. Deleting intent retains remote objects and its ownership journal; deletion does not transfer ownership to a new config UID. Remote pruning, explicit adoption/import, ownership release and live qualification of device attachment/activation is still pending; activation attempts reached Manager but failed on lab prerequisites. The fixture test harness cleans up only its own created IDs in reverse dependency order.

    Native CVK tests

    Normal tests do not contact the lab. Live tests require explicit environment flags and credentials supplied outside Git. The test harness creates temporary credential projections and removes them at completion.

    go test ./internal/controlleradapter/...
go test -race ./internal/controlleradapter/... ./cmd/cisco-vk
# KUBEBUILDER_ASSETS must point to Kubernetes 1.35.0 test binaries.
go test -tags envtest ./internal/controlleradapter/sdwan -run TestEnvtest -v

    Live native lifecycle tests use CVK_SDWAN_LIVE=1 and CVK_SDWAN_MUTATE=1, with SDWAN_URL, SDWAN_USERNAME, SDWAN_PASSWORD and the appropriate TLS setting supplied outside Git. Select the intended TestLive*Lifecycle test explicitly. Live Kubernetes tests additionally use CVK_SDWAN_ENVTEST_LIVE=1 and select a fixture through CVK_SDWAN_ENVTEST_FIXTURE. These tests exercise CVK's native compiler, API client and reconciliation.

    Remaining deployment parity

    Although all pinned resource declarations have CVK implementations, full upstream field/default coverage, advanced classic device-template children, routing and transport/service branches, live qualification of modern policy-object parcels, device attachment/deployment, asynchronous activation recovery, pruning and import are not complete. Reproducible device-level qualification also needs explicit WAN-edge targets and a restoration policy. The BR-2-WAN tag and group association tests used the selected lab router and restored its prior state.

    See the qualification record for measured results and limits.

    Manager 20.18 TrustSec incompatibility

    The pinned provider's TrustSec payload is rejected because data.sxpNodeId is required by this Manager but absent from the provider model. Its default empty devicePassword is also rejected. The reproducible fixture is under examples/configs/sdwan/unqualified/trustsec.yaml; the compiler rejects TrustSec before mutation. Generated TrustSec metadata is retained for further compatibility work and does not count toward qualified coverage.

    Policy-object profile qualification

    policy-profile.yaml defines the singular policy-object profile and fifteen policy parcels. policy-prefixes.yaml, policy-dependencies.yaml and policy-security.yaml exercise the remaining modern policy-object declarations. All 32 child declarations passed native lifecycle under the lab's existing singleton profile; every fixture restored the original child-ID set. CVK did not update or adopt the parent. Creating the singleton profile itself remains unqualified because the lab already has one; that test needs an empty Manager.

    The pinned module uses forwarding_classes where the current documentation calls this collection class_maps. This branch follows the pinned module's name. NaC integer queue and TLOC preference values are encoded as strings for the provider API, with their public numeric constraints retained.

    The pinned module's SNMP groups[].view_variable expression incorrectly traverses group.view.view_variable. That unavailable input is explicitly rejected. AAA accounting_rules[].start_stop_variable is passed verbatim by the module and therefore requires the upstream {{variable}} expression. Other generated parcel variable fields wrap the public variable name as required by their module mapping.

    Classic PIM provider limitation

    The pinned provider does not serialize pim_templates[].rp_addresses[].optional. CVK rejects this field before mutation; the qualified fixture omits it. Other PIM row types preserve their optional flag and provider-defined priority order.

    Tracker references and classic logging compatibility

    Tracker groups require two distinct tracker names declared in the same service profile. CVK creates trackers before groups, resolves controller IDs before every write and comparison, and rejects missing dependencies without sending a mutation.

    The pinned module reads version_ciphersuites_variablevariable for classic logging TLS ciphersuite variables. CVK rejects that typo and ciphersuites_variable; literal ciphersuites is fixture-qualified. Classic IPsec supports nested ike/ipsec fields and the numeric DH-group form shown in the NaC example.
