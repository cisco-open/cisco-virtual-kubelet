  ⚠️  THE CRDs ARE NOT UPGRADED AUTOMATICALLY ON HELM UPGRADE.

  Helm only installs files under crds/ on FIRST install; subsequent upgrades
  leave existing CRDs in place. The required production upgrade order is:

    1. Obtain/unpack the NEW chart version.
    2. Back up live definitions and review the exact CVK CRD diff. A diff exit
       status of 1 means changes were found:

    kubectl get customresourcedefinitions.apiextensions.k8s.io -o yaml \
      > cvk-crds-before-upgrade.yaml
    kubectl diff --server-side --force-conflicts \
      --field-manager=cvk-crd-upgrade -f cisco-virtual-kubelet/crds/

    3. Apply only those reviewed files BEFORE rolling out the new manager.
       Helm owns fields from the initial install, so plain server-side apply
       may conflict:

    kubectl apply --server-side --force-conflicts \
      --field-manager=cvk-crd-upgrade -f cisco-virtual-kubelet/crds/

    4. Verify the additive controller CRDs (and the existing CRDs) are present:

    kubectl get crd networkcontrollers.cisco.vk \
      networkcontrollerconfigs.config.cisco.vk \
      iosxesoftwarerollouts.ops.cisco.vk

    5. Run helm upgrade.

  The force flag is scoped to the exact CRD objects in the reviewed directory;
  never point it at unrelated manifests. Keep the backup through qualification.

  If helm upgrade was already run first, existing CiscoDevice reconcilers stay
  available, but NetworkController reconciliation is disabled for that manager
  process. Apply the CRDs and restart the manager to enable it:

    kubectl rollout restart -n {{ .Release.Namespace }} \
      deploy/{{ include "cisco-virtual-kubelet.fullname" . }}-controller

  ───────────────────────────────────────────────────────────────────────────

  RBAC RECONCILE — the chart updates its ClusterRoles and bindings on every
  Helm upgrade, and Kubernetes applies those permissions without a pod
  restart. If a device worker still reports:

    "iosxediagnostics is forbidden: User <ServiceAccount> cannot list
     resource ..."

  verify that the installed release owns the expected role and binding:

    kubectl auth can-i list iosxediagnostics.config.cisco.vk \
      --as=system:serviceaccount:{{ .Release.Namespace }}:{{ if .Values.topology.enabled }}{{ include "cisco-virtual-kubelet.networkManagementServiceAccountName" . }}{{ else }}{{ include "cisco-virtual-kubelet.vkServiceAccountName" . }}{{ end }} \
      --namespace {{ .Release.Namespace }}

  ───────────────────────────────────────────────────────────────────────────

  ⚠️  MANAGED TOPOLOGY IS ENABLED (KUBERNETES 1.35+ TRUST BOUNDARY).

  Manager leader election is required and enabled. It reduces overlapping
  reconciliation; ledger/CAS and admission remain the durable safety fence.

  policy: {{ include "cisco-virtual-kubelet.topologyPolicyNamespace" . }}/{{ include "cisco-virtual-kubelet.topologyPolicyName" . }}
  ledger: {{ include "cisco-virtual-kubelet.topologyPolicyNamespace" . }}/{{ include "cisco-virtual-kubelet.topologyLedgerName" . }}

  The manager validates the policy selector and the complete versioned admission
  policy/binding pairs before initializing ledger.json with the ledger
  ConfigMap's live UID and binding that UID into the policy annotation. It
  fails closed if admission discovery/type checking, either object identity,
  or the binding is invalid.
  Do not use helm upgrade --force and do not recreate the ledger to clear an
  error. The ledger, policy, admission pairs, and functional profile roles carry
  Helm keep protection; disabling or uninstalling does not retire them. Verify
  all policy bindings and that type checking has no warnings:

    kubectl get validatingadmissionpolicies.admissionregistration.k8s.io \
      -l app.kubernetes.io/instance={{ .Release.Name }}
    kubectl get validatingadmissionpolicybindings.admissionregistration.k8s.io \
      -l app.kubernetes.io/instance={{ .Release.Name }}
    kubectl get validatingadmissionpolicies.admissionregistration.k8s.io \
      -l app.kubernetes.io/instance={{ .Release.Name }} \
      -o jsonpath='{range .items[*].status.typeChecking.expressionWarnings[*]}{.fieldRef}{": "}{.warning}{"\n"}{end}'

  Kubernetes does not type-check these expressions against CRD schemas. Empty
  warnings are necessary but do not replace live API-server denial probes.
  The manager pre-creates retained Node-heartbeat, config-family, and
  disruptive-mutation Leases. Functional workers can update only their exact
  bound objects and cannot create/delete Leases. Do not remove them or recreate
  a same-name CiscoDevice until reservations and maintenance are settled and
  the documented retirement is complete.

  Managed namespaces use at most two shared functional accounts, independent
  of device count:
    app hosting:        {{ include "cisco-virtual-kubelet.appHostingServiceAccountName" . }} ({{ .Values.topology.workerAccounts.appHosting.accessMode }})
    network management: {{ include "cisco-virtual-kubelet.networkManagementServiceAccountName" . }} ({{ .Values.topology.workerAccounts.networkManagement.accessMode }})
  Each account is bound to exactly one fixed profile. App readOnly/disabled
  launches no app worker and leaves Nodes unschedulable. Network readOnly runs
  only telemetry, diagnostics, and read-only operations; configuration and
  gNOI mutation need readWrite. Native admission remains the object-level
  boundary for the namespace-shared identities.
  Resolved account names are cluster-reserved by admission. If you override
  either derived name, keep it unique across every CVK release.

  ServiceAccounts are namespaced: these are the only two functional identities
  defined per managed CiscoDevice namespace, not two cluster-global accounts
  and not two accounts per device. A disabled plane is removed. Access-mode
  changes drain the old worker objects before RBAC is replaced or revoked.

  Managed-device namespaces must be dedicated and administrator-controlled.
  Do not grant tenant edit/admin, ServiceAccount impersonation, either shared
  account, worker Pod logs/exec/attach/portforward/proxy, scale, or delete
  authority. ClusterRoleBinding writers remain a cluster-admin trust boundary.
  Kubelets must authenticate as system:node:<nodeName> with the Node and RBAC
  authorizers and NodeRestriction enabled.

  CONFIG_LEASE_NAMESPACE is bootstrap-immutable (current value:
  {{ .Values.config.leaseNamespace | default "<device namespace>" }}). Retire
  managed topology and re-enroll before moving Lease authority.
{{- if .Release.IsUpgrade }}

  During migration, exact preexisting shared worker bindings are retained with
  topology.cisco.vk/retire-shared-worker-access=rollout-v1. Do not delete that
  bridge manually. The manager removes it only after all shared-identity
  Deployments, ReplicaSets, and Pods are quiesced and replacements are audited;
  first managed admission remains deferred until that retirement completes.
  Any PR #190-era UID-derived worker identities are transitional as well; the
  manager removes only exact owned accounts/bindings after the split workers
  are audited. Steady state is the two functional accounts shown above.

  This migration requires a live Helm upgrade because lookup supplies the
  existing binding identities. Offline helm template / GitOps pruning is not a
  supported migration path unless existing CVK RBAC is excluded from prune
  through controller-reported retirement completion.
{{- end }}

  Planner, approver, topology-author, policy-admin, and ledger-breakglass roles
  are intentionally unbound. Delegate only the roles required in each target
  namespace. See charts/cisco-virtual-kubelet/README.md before enrolling a
  CiscoDevice or changing policy.
